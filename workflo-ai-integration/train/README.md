# Adapter training pipeline

Produces the three real LoRA adapters (`test-gen`, `reasoning`, `reporting`)
and the frozen artifact manifest from real files only. Nothing in this
directory fabricates weights: GGUFs come from a real training run followed by
llama.cpp conversion, and every hash is computed from actual bytes.

## Pipeline

```
dataset_sources.py          authoritative examples (reviewable Python)
        │  build_datasets.py
        ▼
datasets/*.jsonl            ChatML records, one JSON object per line
        │  validate_datasets.py   ← same schemas + safety gates as serving
        ▼
train_qlora.py              QLoRA on ORIGINAL HF weights (GPU required)
        ▼  train/out/<task>/final
convert_peft_to_gguf.py     wraps llama.cpp convert_lora_to_gguf.py
        ▼  serving/adapters/<task>.gguf
make_manifest.py            hashes real files → serving/model-artifacts.json
        ▼  scripts/verify_artifact_manifest.py (run automatically)
release-ready artifact block
```

## Step-by-step

```bash
cd workflo-ai-integration

# 1. Build + validate datasets (CPU, seconds)
python train/build_datasets.py
python train/validate_datasets.py

# 2. Train each adapter (GPU host; >=16 GB VRAM for a 4B base)
pip install -r train/requirements-train.txt
python train/train_qlora.py --task test_gen \
    --dataset train/datasets/test_gen.jsonl \
    --base-model Qwen/Qwen3-4B \
    --output-dir train/out/test_gen --epochs 3
python train/train_qlora.py --task reasoning \
    --dataset train/datasets/reasoning.jsonl \
    --base-model Qwen/Qwen3-4B \
    --output-dir train/out/reasoning --epochs 3
python train/train_qlora.py --task reporting \
    --dataset train/datasets/reporting.jsonl \
    --base-model Qwen/Qwen3-4B \
    --output-dir train/out/reporting --epochs 3

# 3. Convert each adapter against the pinned llama.cpp checkout
python scripts/convert_peft_to_gguf.py --peft-dir train/out/test_gen/final \
    --hf-config-dir <original HF weights dir> \
    --base-gguf serving/models/base.gguf --llamacpp-dir /path/to/llama.cpp \
    --out serving/adapters/test-gen.gguf
# (repeat for reasoning + reporting)

# 4. Smoke each adapter against llama-server, then generate the manifest
python train/make_manifest.py \
    --image "ghcr.io/<org>/llama.cpp:server@sha256:<64hex>" \
    --model-id "<frozen-model-id>" \
    --base-source "<canonical base source>" \
    --adapter-source "<canonical adapter source (includes run id)>"
```

## Rules this pipeline enforces

1. **No synthetic GGUFs.** Conversion delegates to llama.cpp's converter and
   fails closed if it is missing. The manifest generator refuses to write
   unless all four artifacts exist, and re-runs the verifier before exiting.
2. **Datasets share the serving contract.** validate_datasets.py applies the
   exact `WriteTestCall` / `ProposeInvariantCall` / `ReportNarrative` schemas
   and the exact `compile_check` / `property_expr_check` gates the router
   applies at request time. If a dataset can't pass the gates, it would teach
   the model output that gets discarded in production.
3. **Privacy.** Reporting examples contain structured outcomes only — never
   source. Test bodies are self-contained synthetic examples with no customer
   code, no secrets, and no real hostnames.
4. **Weights never enter Git.** `*.gguf` is git-ignored; the generated
   `serving/model-artifacts.json` stays out of version control until the
   release owner authorizes versioning of identities (paths + digests only,
   never weights).

## Base-model note

`train_qlora.py` trains against the ORIGINAL Hugging Face weights
(`--base-model Qwen/Qwen3-4B` or the matching SFT source). The serving GGUF
(`serving/models/base.gguf`, a Q4_K_S quant) is used only at conversion and
serving time. The three must describe the same architecture; record the exact
HF revision used for training in the release evidence.
