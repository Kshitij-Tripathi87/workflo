# workflo Sandbox Contract

The sandbox contract defines the input, output, and behavioral promises of
the workflo sandbox executor. This document is the source of truth for
claims made in the demo — if a claim isn't here, it isn't true.

## Input

A run accepts one thing: a `SandboxSpec` (see
`packages/core-schema/src/tenant_shield_schema/sandbox.py`).

| Field | Meaning |
|---|---|
| `sandbox_id` | One-time ID for this run. Generated by the CLI; never reused. |
| `repo_url` | Git URL to clone inside the sandbox |
| `commit_sha` | Optional pinned commit. If absent, HEAD is used. |
| `run_spec` | The RunSpec dict passed through to the worker-engine payload |
| `timeout_seconds` | Hard timeout. Default 600 (10 min), range 10-3600. |
| `memory_mb` | Memory limit. Default 2048, range 256-16384. |
| `cpu_cores` | CPU core limit. Default 2.0, range 0.5-8.0. |
| `allowed_egress_hosts` | Host allowlist. Empty (default) = no egress. |

## Output

A run produces one thing: a `SandboxRunResult` (see
`apps/sandbox-executor/src/workflo_executor/executor.py`) containing:

- `receipt: SignedReceipt` — the customer-facing artifact. This is what
  survives. Nothing else does.
- `report: RunReport` — test counts and findings, never source code.
- `lifecycle_events: list[SandboxLifecycleEvent]` — chronological audit
  trail embedded in the receipt.
- `elapsed_seconds` — wall-clock time.
- `success: bool` — True iff every one of these is true:
  - `report.failed == 0`
  - Container was not timed out
  - `teardown_proof.container_removed`
  - `teardown_proof.filesystem_removed`
  - `canary_check.request_succeeded == False`
- `error: Optional[str]` — human-readable failure reason if not success.

## Behavioral Promises

| # | Promise | How it's enforced |
|---|---|---|
| P1 | The sandbox runs in a Docker container with `--network none` | `ContainerConfig.network_mode = "none"` is the default and CLI default |
| P2 | The repo is cloned onto a tmpfs mount (RAM-backed) | `mount_tmpfs()` in `ephemeral_fs.py`; unmount + verify_ephemeral_gone after |
| P3 | The sandbox cannot reach the network during inference | A canary request is attempted every run; failure is logged in the receipt |
| P4 | The sandbox is destroyed after every run, with no residue | `verify_container_gone()` + `verify_ephemeral_gone()`, both fail-closed |
| P5 | Every run produces a signed, tamper-evident receipt | `ReceiptSigner.sign()` over `canonical_payload()` using Ed25519 |
| P6 | Even a failed run produces a signed receipt | The executor's exception handler builds and signs a failure receipt |
| P7 | The signed receipt verifies against a published public key | `verify_receipt_signature()` is standalone; no signer needed |
| P8 | The teardown proof fails closed | `verify_container_gone()` returns False on any error |

## Not Claimed (Post-Demo)

The following are **designed but not implemented**. They must not be
demoed, mentioned as working, or enabled via any flag before Aug 25.
If any of this shows up in code before then, that is a bug in the
process, not a feature.

- **Shared inference service.** `--deep-test` uses the embedded model
  only (Ollama + Qwen2.5-Coder inside the sandbox, weights never leave
  the container, teardown wipes `~/.ollama`). There is no external
  model service, no allowlisted destination, and no network exception
  to P1/P3 above.
- **`NetworkMode.INFERENCE_ONLY`.** Does not exist. `ContainerConfig.network_mode`
  has exactly one live value: `"none"`.
- **Any Docker network other than the default isolated one.** No sandbox
  attaches to a custom or `--internal` network. No `vllm-openai`
  container runs anywhere in this stack.
- **`SharedInferenceAttestation` on the receipt.** Not a field. Adding
  an attestation field that's always empty, or that depends on a
  service that doesn't exist, is worse than not having the field —
  it's a claim the receipt can't back up.
- **A dual-canary check.** `workflo verify` treats Claim P3 as
  "canary request failed." A receipt requiring a *successful* inference
  health check alongside a *failed* general-egress check does not exist,
  and must not be added under demo pressure — it would either break
  verification for every existing receipt or require a verifier change
  that hasn't been reviewed.

**What the demo may say instead:** the sandbox is `--network none`.
The canary to `example.com` fails, every time, by design. `--deep-test`
runs entirely inside that same sealed container. That is the strongest
isolation story available today, and it is the one that's actually
built.

**First post-demo ticket, when this resumes:** `NetworkMode.INFERENCE_ONLY`
alone — a dedicated `--internal` Docker network and three reachability
tests (inference-service reachable, general egress blocked, blocked
even from the host), repeated ten times with no flakiness. No client,
no vLLM, no receipt fields, no CLI flag, until that's boring. Steps 2–6
follow only after that, in order, with the default `--deep-test` tier
switching to shared inference as the *last* change, not the first.

## Sandbox Lifecycle

```
SandboxSpec
    |
    v
[mount_tmpfs] --------------------------------------------------> emit("tmpfs_mounted")
    |
    v
[git clone --depth 1 <repo_url> <tmpfs/repo>] -----------------> emit("repo_cloned")
    |
    v
[git checkout <commit_sha>] (if pinned) ------------------------> emit("commit_pinned")
    |
    v
[docker create --network none --memory <m> --cpus <c>] -------> emit("container_created")
    |
    v
[docker start] --------------------------------------------------> emit("tests_started")
    |
    v
[docker wait <container>] (with timeout) -----------------------> emit("tests_completed" | "tests_timeout")
    |
    v
[parse RunReport from stdout: WORKFLO_REPORT: {json}]
    |
    v
[attempt_canary_request] ---------------------------------------> emit("canary_checked")
    |
    v
emit("teardown_started")
    |
    v
[docker rm -f <container>]  ---->  [unmount_tmpfs]  ---->  [verify_ephemeral_gone]
    |
    v
emit("destroyed")
    |
    v
[build TeardownProof] (fails closed)
    |
    v
emit("receipt_signed")
    |
    v
[SignedReceipt] = (sandbox_id, issued_at, report, proof, canary, events, signature)
    |
    v
[signer.sign(receipt)]  (Ed25519 over canonical_payload())
    |
    v
return SandboxRunResult
```

### Live Docker Smoke Test (manual — requires Docker Desktop running)

The 78 unit tests mock Docker so they run anywhere. The live smoke test
requires a real Docker daemon + the `workflo-worker:latest` image. Run it
with:

```bash
# 1. Start Docker Desktop
# 2. Build the worker image (Phase 2 will provide the Dockerfile):
#    docker build -t workflo-worker:latest apps/worker-engine/

# 3. Dry-run validates everything except Docker:
workflo run --repo https://github.com/psf/requests.git --test --security --dry-run

# 4. Live run (real clone + container + canary + teardown):
workflo run --repo https://github.com/psf/requests.git --test --security --output report.json

# 5. Verify the receipt signature against a published pubkey:
workflo keygen --output pubkey.pem --force
workflo verify --receipt report.json --pubkey pubkey.pem
```

Expected: `VERIFIED: receipt signature is valid.` and `Run complete: SUCCESS`.

## Risk: Docker not available

When Docker isn't installed (CI, dev), the spike simulates the network
isolation check. The full pipeline still requires Docker to run end-to-end.
For local development without Docker, the spike's fallback path validates
the canary mechanism.

```bash
docker run --rm --network none python:3.11-slim python -c "import urllib.request; urllib.request.urlopen('https://example.com')"
```

Expected: failure. If this succeeds, `--network none` is not blocking egress.

## Risk: Customer repos that require `pip install` before tests

The sandbox runs with `--network none`, which means the customer's repo
tests **cannot `pip install` their dependencies at test time**. The default
`workflo-worker` image contains pytest, Playwright, and Python's stdlib —
nothing else. For a repo whose tests do `import requests` or `import django`
or any other third-party module, the surface test will report 0 collected
or failure by ImportError.

This is **by design**, not a bug:

1. Installing deps inside the sandbox at test time requires network access, which the canary exists to prove is blocked.
2. Blindly `pip install -r requirements.txt` from customer code before network seizure is a supply-chain trust boundary — the run would have to trust an arbitrary PyPI dependency set chosen by the customer.
3. Phase 2 introduces a `workflo-worker-<repo_name>` per-repo image build path that bakes the repo's deps in at *image-build* time (network-on), then runs the sandbox network-off.

For Phase 1 validation, the **surface-test contract** is:
- repos whose tests have import-level deps that aren't already in `workflo-worker:latest` will report 0 tests collected (or ImportError) and a failed receipt — this is the correct, safe answer.
- Repos with no install-time deps (stdlib-only) should run cleanly and report pass/fail counts correctly.

Use repos like `pallets/click` (Python stdlib tests), or the bundled `tests/fixtures/fixture_repo` repo, for surface validation pass. **Do not use `psf/requests`** — its `tests/conftest.py` does `from requests.compat import urljoin` at import time, which requires `requests` to be already installed.
